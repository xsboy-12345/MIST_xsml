# XLSum Judge Fine-Tuning

Fine-tune **Llama-3.1-8B-Instruct** and **Qwen2.5-7B-Instruct** as multilingual summary quality judges using human evaluation data from the WMT25-MIST shared task.

## Task

Given a set of reviews and a generated summary, the model scores the summary on four dimensions (1–7 Likert scale):

| Dimension | Description |
|-----------|-------------|
| Faithfulness | Is all information in the summary supported by the reviews? |
| Coverage | Are the most important review points covered? |
| Naturalness | Is the summary fluent and natural in the target language? |
| Coherence | Is the summary logically sound and internally consistent? |

Training signal comes from human annotations. Fine-tuning quality is measured by **Kendall's τ** correlation and **ranking accuracy** against human scores.

## Data

### Source

Data comes from the **WMT25-MIST shared task** (Multilingual Instruction-following and Summarization Task), specifically the cross-lingual summarization (XLSum) subtask.

- **Original reviews**: Google Maps restaurant reviews and Amazon product reviews, collected in multiple languages
- **Summaries**: Generated by 17 LLMs asked to summarize the reviews in the target language
- **Human annotations**: Each summary is rated by human annotators on 4 quality dimensions (1–7 Likert scale)

The raw file used is `data/raw/xlsum_humeval.json`, which is the human evaluation split from WMT25-MIST.

### Statistics

| Field | Value |
|-------|-------|
| Tasks (unique review sets) | 252 |
| Total records (task × model) | 4,284 |
| Languages | 14 |
| Generator models | 17 |
| Human-rated dimensions | 4 |

**Languages**: Arabic, Czech, German, Spanish, French, Hindi, Indonesian, Italian, Japanese, Korean, Russian, Swedish, Turkish, Chinese

**Generator models**: GPT-4.1, Gemini-2.5-Pro, Claude-4, DeepSeek-V3, Llama-3.1-8B, Llama-4-Maverick, Qwen2.5-7B, Qwen3-235B, Mistral-7B, Mistral-Medium, CommandA, CommandR7B, AyaExpanse-8B, AyaExpanse-32B, Gemma-3-12B, Gemma-3-27B, TowerPlus-72B

### Training data construction

Each humeval record is expanded into 4 training examples (one per dimension), giving **17,136 samples** total, split 80/10/10.

| Split | Size |
|-------|------|
| train | 13,708 |
| dev   | 1,713  |
| test  | 1,715  |

## Quickstart

### 1. Prepare data

```bash
python data/prepare.py
# → data/processed/train.jsonl, dev.jsonl, test.jsonl
```

Optionally filter out low-quality records:

```bash
python data/prepare.py --min-score 2.0
```

### 2. Visualize training data (local)

EDA plots saved to `viz/figures/data/`: score distributions per dimension, language distribution bar chart, language × dimension heatmap, and per-generator model mean scores.

```bash
python viz/plot_data.py
```

### 3. Fine-tune on GPU server

```bash
# Install dependencies on the server
pip install -r requirements.txt

# Fine-tune Llama-3.1-8B-Instruct
python train/train.py --config train/configs/llama_config.yaml

# Fine-tune Qwen2.5-7B-Instruct
python train/train.py --config train/configs/qwen_config.yaml

# Smoke test (2 steps only, no GPU memory pressure)
python train/train.py --config train/configs/llama_config.yaml --dry-run
```

Training automatically computes **Kendall's τ on the dev set after every epoch** and saves the log to `logs/{model}_tau_log.json`. The final adapter is saved to `outputs/{model}/adapter_final/`.

### 4. Run inference

**Fine-tuned model (on GPU server):**

```bash
python eval/predict.py \
    --adapter outputs/llama/adapter_final \
    --model-name llama-judge
# → eval/outputs/llama-judge.json

python eval/predict.py \
    --adapter outputs/qwen/adapter_final \
    --model-name qwen-judge
# → eval/outputs/qwen-judge.json
```

**Zero-shot baseline (base model only, no adapter):**

```bash
python eval/predict.py \
    --base-model meta-llama/Llama-3.1-8B-Instruct \
    --model-name llama-zero-shot

python eval/predict.py \
    --base-model Qwen/Qwen2.5-7B-Instruct \
    --model-name qwen-zero-shot
```

Both modes use a `DigitOnlyLogitsProcessor` that restricts generation to tokens `1`–`7`, preventing the model from continuing in the input language.

Both modes also **quantize to 4-bit NF4 by default**, matching the precision `train.py` trains and dev-evaluates under (see Known Issues below). Pass `--full-precision` to load the model unquantized instead — mainly useful for deliberately comparing quantized vs. full-precision numbers.

### 5. Compute evaluation metrics

```bash
python eval/compute_tau.py \
    --pred eval/outputs/llama-zero-shot.json \
           eval/outputs/llama-judge.json \
           eval/outputs/qwen-zero-shot.json \
           eval/outputs/qwen-judge.json
# → eval/outputs/tau_report.json
```

### 6. Visualize results (local)

Sync logs and predictions from the server, then generate all plots:

```bash
rsync -av server:~/xlsum/logs/         logs/
rsync -av server:~/xlsum/eval/outputs/ eval/outputs/

python viz/plot_training.py
# → viz/figures/training/
```

Figures produced:

| File | Description |
|------|-------------|
| `tau_curves.png` | Dev τ per epoch (training curves) |
| `version_comparison.png` | Test τ and ranking accuracy bar charts |
| `scatter_pred_vs_human.png` | Predicted vs. human score scatter per model × dimension |
| `score_distribution_comparison.png` | Score distribution: predicted vs. human |
| `tau_radar.png` | Per-dimension τ radar chart comparing all models |

To regenerate only the training curves (no inference needed):

```bash
python viz/plot_training.py --tau-only
```

### 7. Dataset browser (local)

Interactive PyQt6 GUI to browse and filter training records by language, dimension, and score range.

```bash
conda install -c conda-forge pyqt6
python viz/editor.py              # opens train split by default
python viz/editor.py --split test
```

- Filter by language / dimension / minimum score
- Browse reviews, generated summary, and human scores side by side
- Export filtered subset to JSONL (Ctrl+E)

## Training Format

Each training sample uses the model's native chat format:

```
System: You are an expert multilingual evaluation assistant. Given a set of
        reviews and a summary, score the summary on the specified criterion
        using a scale from 1 to 7. Output only the integer score.

User:   Score the following summary based on FAITHFULNESS (1-7).
        ...
        Language: Turkish
        Reviews:
        [1] Delicious food, great atmosphere...
        Summary: Bu restoranın atmosferi temiz ve sıcak...
        Faithfulness score (1-7):
Assistant: 5
```

Loss is computed **only on the assistant token** (`5` in this example); prompt tokens are masked out with `-100`.

## Model Configuration

Both models use QLoRA (4-bit NF4) + LoRA. Key hyperparameters (v2):

| Parameter | Llama-3.1-8B | Qwen2.5-7B |
|-----------|-------------|------------|
| LoRA rank | 32 | 16 |
| LoRA alpha | 64 | 32 |
| LoRA dropout | 0.05 | 0.1 |
| Target modules | q/k/v/o/gate/up/down\_proj | q/k/v/o/gate/up/down\_proj |
| Quantization | 4-bit NF4 | 4-bit NF4 |
| Learning rate | 1e-4 | 1e-4 |
| LR scheduler | cosine | cosine |
| Warmup steps | 100 | 100 |
| Weight decay | 0.01 | 0.05 |
| Epochs | 8 | 8 |
| Effective batch size | 16 | 16 |

## Evaluation Metrics

| Metric | Description |
|--------|-------------|
| Kendall's τ | Rank correlation between predicted and human scores, per dimension and averaged |
| Ranking accuracy | Pairwise ranking agreement across generator models (0.5 = random) |

Zero-shot baselines (base model without fine-tuning) are included for comparison.

## Version History & Known Issues

Both models have gone through 3 training rounds so far. All logs/results are kept (`logs/*_v1/v2/v3_tau_log.json`, `eval/outputs/*-judge-v1/v2/v3.json`) for traceability — nothing has been overwritten.

| Version | What changed | Status |
|---------|-------------|--------|
| v1 | Initial LoRA config (r=16, 5 epochs, lr=2e-4) | Baseline, superseded |
| v2 | Tuned LoRA config for better generalization (higher rank/alpha, more target modules, 8 epochs, lower lr, more warmup) — see `train/configs/*.yaml` history | Best test-set result so far |
| v3 | **Same config as v2** (only `output_dir` renamed). The actual change was in the *evaluation* code: `TauCallback.evaluate_tau` in `train/train.py` was switched from free-form generation (`max_new_tokens=4` + regex) to the same digit-only constrained decoding used by `eval/predict.py` (`max_new_tokens=1` + `DigitOnlyLogitsProcessor`), so training-time dev metrics would be measured the same way as the final test-set metrics. | See known issue below |

### Known issue: v3's per-epoch dev τ log is unreliable

`logs/llama_v3_tau_log.json` and `logs/qwen_v3_tau_log.json` show dev τ collapsing to near-zero/random from epoch 1 onward (e.g. llama: 0.02 vs. v2's 0.16; qwen: 0.01 vs. v2's 0.32; `naturalness` even goes negative). This looks like a training failure, **but it isn't** — `eval/predict.py` run on the same final `adapter_final` checkpoints gives normal, v2-comparable test τ (llama 0.114, qwen 0.097; see `eval/outputs/tau_report.json`).

Leading hypothesis: a **quantization precision mismatch** between the two evaluation call sites.
- `train/train.py`'s `TauCallback` calls `model.generate()` on the model **as loaded for training** — 4-bit NF4 quantized (`use_4bit: true` in the config).
- `eval/predict.py` used to load the adapter **without quantization** by default.

Once generation is hard-restricted to only 7 candidate tokens (digits 1–7), the choice becomes very sensitive to small logit differences — quantization noise is enough to flip the argmax during training-time eval, while a full-precision pass doesn't have that noise. This would explain why the *dev* curve looks broken but the *test* numbers don't.

**Status: fixed, not yet re-verified.** The v3 `adapter_final` checkpoints were lost in a remote instance reset before this could be confirmed directly (re-running `predict.py` under quantization on the *same* v3 weights would have been the clean test). As of this commit, `eval/predict.py` now **quantizes by default** (4-bit NF4, matching `train.py`'s `TauCallback`) — pass `--full-precision` to opt out. This means:
- Going forward, `TauCallback` and `predict.py` evaluate under the same precision, so a v4 dev-τ curve that stays healthy (instead of collapsing like v3's) would confirm the hypothesis.
- The **existing** `eval/outputs/tau_report.json` numbers for zero-shot/v1/v2/v3 were all generated under the *old* full-precision default — they are not directly comparable to future quantized-default runs. Re-run `predict.py` (now quantized by default) on the still-available v1/v2 adapters if you need a like-for-like comparison against v4.

**Practical takeaway for now**: trust `eval/outputs/tau_report.json` (test-set, from `predict.py`) over the `logs/*_v3_tau_log.json` per-epoch curves — the latter should not be used to judge whether v3 training "worked." A v4 run is planned now that `TauCallback` and `predict.py` evaluate under matching precision; v1–v3 artifacts stay untouched for comparison.
